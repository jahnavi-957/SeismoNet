# Sample upload files

These CSVs exist so the web demo can be run without the multi-gigabyte INSTANCE dataset.

## `demo_12traces_predict.csv`

| | |
|---|---|
| Size | 2.0 MB |
| Rows | 36,864 data rows (12 traces × 3,072 samples) |
| Columns | `trace_id, sample_index, E, N, Z` |
| Upload as | prediction mode (no reference columns) |
| Result | twelve windows, each with a P pick, an S pick and both probability curves; 11 of the 12 have both phases picked |

Each block of 3,072 consecutive rows sharing a `trace_id` is one 30.72-second window at 100 Hz.
Map **Trace ID → `trace_id`** on the mapping step (the other columns auto-detect) or every row collapses
into a single trace.

## What these waveforms are — and are not

They are **synthetic demonstration windows**, not raw field recordings:

- The trace ids and their reference P/S arrivals come from the frozen validation predictions
  (`runs/validation_inference_p6_seed42/predictions.json`) and `backend/demo_traces.json`.
- The samples themselves are generated by `SeismoInferenceEngine._analyze_demo_trace`: band-limited noise
  with wavelets placed at the reference arrivals.

So this file demonstrates that the software path works end to end — CSV parsing, contract checks,
normalisation, frozen-checkpoint inference, thresholding, charts. It is **not** a scientific evaluation, and
metrics computed on it say nothing about model quality. The model's real numbers are the held-out test
results on the Model Evaluation page: P F1 0.685, S F1 0.499.

Two behaviours to expect when demonstrating:

- In some traces the predicted S arrival lands slightly **before** the predicted P arrival (the synthetic
  bursts confuse the model). Pick trace 1, 3, 5, 8, 10, 11 or 12 for a clean P-then-S demonstration.
- Uploaded CSVs are request data only; they are never added to a training, validation or test split.

## Regenerating

With the backend running on port 8000:

```powershell
.venv\Scripts\python.exe scripts\make_demo_csv.py --traces 12 --out samples\demo_12traces_predict.csv
.venv\Scripts\python.exe scripts\make_demo_csv.py --traces 12 --labeled --out samples\demo_12traces_labeled.csv
```

The upload limit is 50 MB / 100,000 rows, so one CSV can hold at most **32 traces** of 3,072 samples
(32 × 3,072 = 98,304 rows). To reach the other demo traces, page through with `--offset` — the 210 traces are
covered by seven files:

```powershell
# 6 files of 32 traces + 1 of 18 = all 210 demo traces
0,32,64,96,128,160 | ForEach-Object { .venv\Scripts\python.exe scripts\make_demo_csv.py --traces 32 --offset $_ --out "samples\demo_32traces_part.csv" }
```

Measured: a 32-trace file uploads and analyses in **14–17 s** on CPU — parsing the 98k rows takes longer than
the inference itself. The results page then offers all 32 traces in its selector.

### A note on the `--labeled` variant

`--labeled` writes `p_arrival_sample` / `s_arrival_sample` in **window** coordinates, which is what the
comparison page expects: a window is a crop of the 12,000-sample record, so the window-relative reference is
`absolute − window_start`. (Before 2026-10-25 the generator wrote the absolute value, which added a constant
~5.5 s offset to every residual — see change-log entry `2026-10-25-010`.)

Even with correct references, **do not present the labeled variant as a model evaluation**. The synthetic
bursts are picked about 500–700 ms early, which is far outside the frozen ±200 ms tolerance, so comparison mode
reports zero true positives on all twelve traces. Use it only to show that the comparison machinery works;
use the prediction-mode file for the actual demonstration.
