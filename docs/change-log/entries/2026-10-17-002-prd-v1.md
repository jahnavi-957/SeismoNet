## B. What was changed?

**Previous behaviour.** `PRD.md` was a v0.1 draft (657 lines) written from domain knowledge. It was methodologically strong — every item labelled `[GIVEN]`, `[DERIVED]`, `[PROPOSED]` or `[OPEN]`, and an explicit policy of not inventing requirements or performance targets — but it used a non-sequential requirement ID scheme (`FR-D1`, `FR-P3`, `FR-M5`, …), and it lacked several sections a professional PRD normally carries.

**New behaviour.** `PRD.md` is now a full v1.0 document structured as: Document Control; Executive Summary; Problem Statement; Background and Scientific Context; Vision and Objectives; Target Users and Use Cases; Scope; Functional Requirements; Non-Functional Requirements; Scientific and Model Requirements; Dataset Requirements; Evaluation Metrics; Research Experiments; Risks and Mitigation; Milestones and Deliverables; Acceptance Criteria; Assumptions and Open Questions; plus an identifier-mapping appendix, a glossary and an approval record.

Specific structural changes:

1. **Sequential requirement IDs.** `FR-001`…`FR-084`, `NFR-001`…`NFR-015`, `SR-001`…`SR-017`, `DR-001`…`DR-007`.
2. **Every functional requirement now has** a priority, dependencies, an explicit acceptance criterion, and a verification method (unit test / integration test / inspection / measured / visual / documented procedure). v0.1 kept acceptance criteria in user stories instead.
3. **New sections added:** Document Control with change history; a dedicated **Scientific and Model Requirements** section (§10) covering input representation, channel ordering, sampling-rate policy, window-length policy, normalisation, target representation, loss, architecture, training/validation, checkpoint selection, threshold selection, peak detection, missing-phase handling and timestamp conversion — each with an explicit rationale and a status tag; a **Dataset Requirements** section (§11) that separates confirmed properties from assumptions; and **Acceptance Criteria** (§16) split into minimum viable prototype, full project, and optional improvements.
4. **Non-functional requirements rewritten** to the requested categories (reproducibility, reliability, maintainability, performance, memory efficiency, portability, data integrity, testability, documentation, usability, licensing, honest scope, security) with measurable targets **only** where justified and `TBD` markers where not.
5. **Old→new ID mapping** added as §18 so that every v0.1 identifier can be resolved.
6. **Risks expanded** from `R1`–`R8` to `R-01`–`R-18`, each linked to a requirement.
7. **Open questions expanded** from `OQ-1`–`OQ-20` to `OQ-1`–`OQ-23` (three added: checkpoint-selection criterion; overlapping-target handling; repository hygiene items).

**Preserved unchanged:** all v0.1 substance, the `[GIVEN]/[DERIVED]/[PROPOSED]/[OPEN]` labelling system, the "do not invent" policy, and the identifiers `G1`–`G7`, `NG1`–`NG6`, `A1`–`A6`, `US-01`–`US-17`, `SC-1`–`SC-8`, `OQ-1`–`OQ-20`, `E1`–`E38`, `O1`–`O4`. The 38 edge cases and 17 user stories were **not** restated in full; they remain in the archive and are cross-referenced by ID.

## C. Why was this change necessary?

The task required a complete, professional PRD suitable for a university research project, an engineering team and an evaluation panel, with sequential requirement IDs and per-requirement acceptance criteria and verification methods.

Beyond the task instruction, there were concrete gaps that would have caused problems later:

1. **No acceptance criterion per functional requirement.** Without one, "is `FR-D4` done?" had no answer. The rewritten requirements each carry a checkable criterion.
2. **No explicit scientific-parameter section.** Parameters such as σ, window length, normalisation policy and tolerance were scattered across the document and `tech.md`. A reader could not find the authoritative statement of a scientific convention, which is exactly where an arbitrary choice could be silently introduced later.
3. **Acceptance criteria conflated with user stories.** User stories are for the domain reader; acceptance criteria are for the implementer. Separating them makes both usable.
4. **Open questions not linked to the requirements they block.** v0.1 listed open questions in one table; the new document states, per question, which requirements it affects.
5. **Section 0 of v0.1 explicitly warns** that no literature lookup was performed and that dataset statistics and citations must be verified. That warning had to be carried forward prominently rather than buried, because a later reader could otherwise quote unverified material as fact.

**Evidence:** the audit (`docs/AUDIT_REPORT.md` §5.2) enumerated the gaps in v0.1 relative to the requested structure, and the task specification enumerated the required sections.

## D. Why was this approach chosen?

**Chosen approach:** author a new v1.0 PRD in the same file path, preserve v0.1 verbatim in `docs/archive/`, and carry a full identifier mapping so nothing is orphaned.

**Alternatives considered:**

| Alternative | Assessment | Why not chosen |
|---|---|---|
| Edit v0.1 in place without archiving | Simple | Destroys the v0.1↔v1.0 diff and loses the original edge-case/user-story prose; forbidden by the change-log rules on preserving history |
| Write v1.0 as a *new* file and leave `PRD.md` as v0.1 | Non-destructive but creates two PRDs | A repository with two competing PRDs invites contradiction. The convention adopted is: the current document has the canonical path (`PRD.md`); superseded versions live in `docs/archive/` with a version suffix |
| Keep v0.1's ID scheme and add the missing columns | Minimal disruption | The task explicitly requires sequential IDs (`FR-001`, `FR-002`, …). Sequential IDs also make coverage checks (`every FR is covered by a phase`) tractable, which the v0.1 scheme did not |
| Rewrite from scratch and discard v0.1 content | Clean slate | Would gratuitously lose a genuinely careful draft, including 38 edge cases and 20 open questions. The v0.1 content is good; only its structure was insufficient |
| Restate the 38 edge cases and 17 user stories in full in v1.0 | Maximum completeness in one file | Would duplicate several thousand words and create a second copy that can drift. Cross-referencing by ID with the archive as the single source is the lower-maintenance choice |

**Trade-offs accepted:** the PRD is long (approximately 1,000 lines); a reader now needs the archive to see the edge-case prose; the mapping section adds overhead. These are accepted in exchange for non-destructive versioning and traceability.

## E. How was it implemented?

1. **Read all three original documents completely** (`README.md`, `PRD.md`, `tech.md`) before editing anything, as required by the "inspect before editing" rule.
2. **Audited the repository** and recorded the gaps in v0.1 in `docs/AUDIT_REPORT.md` §5.2 (an evidence-backed list of what the draft lacked).
3. **Copied** `PRD.md` to `docs/archive/PRD-v0.1-original.md` before modifying the original.
4. **Authored the new `PRD.md`** with the 17-section structure plus appendices. Key implementation decisions inside the document:
   - Requirement groups follow the domain, not the v0.1 grouping: dataset ingestion, input validation, metadata, preprocessing, targets, splitting, augmentation, model, training, checkpointing, inference, evaluation, visualisation, experiments, export, optional UI, reproducibility.
   - Each requirement row carries: ID, description, priority, dependencies, acceptance criteria, verification method, and source tag.
   - Scientific parameters are stated once, in §10, with rationale and a status tag, and are referenced from the functional requirements rather than duplicated.
   - §16 acceptance criteria were split into MVP / full / optional, matching the task's requirement to separate them.
   - §18 provides the old→new mapping in two tables, including the several v0.1 requirements that map to more than one new requirement.
5. **Reconciled the milestone plan** with the roadmap phases that were being authored in parallel, and with the new `SC-9`/`SC-10` criteria and `SCF-*`/`SCO-*` criteria.
6. **Verified** the resulting document for internal consistency: every `FR-*` has an acceptance criterion; the mapping table accounts for every v0.1 requirement; every `[OPEN]` value in §10 and §12 appears in §17.2.

## F. How did this improve SeismoNet?

- **VERIFIED (checkable completeness).** Every functional requirement in §8 now has an acceptance criterion and a verification method. This is checkable by reading the table, and was checked.
- **VERIFIED (traceability).** Every v0.1 identifier resolves through §18 to a v1.0 identifier or a preserved identifier. Checked against the v0.1 document.
- **EXPECTED (implementability).** A developer can now determine, for any requirement, its dependencies, its acceptance criterion and how it will be verified — the three things that were previously absent.
- **EXPECTED (honesty).** The unverified-literature warning is now prominent in both §4 and §11.3, with per-candidate `UNVERIFIED` tables, reducing the risk of an unverified citation being quoted as fact.
- **EXPECTED (scientific defensibility).** §10 records a rationale for every scientific parameter, which is what allows the report to answer "why σ = 10?" with a reason rather than a recollection.
- **No claim is made that the PRD improves model accuracy or performance.** A requirements document cannot do that. What it enables is a defensible, checkable implementation.
